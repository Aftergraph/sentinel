## Unit hardening: MemoryDenyWriteExecute removed

PR #41 shipped `MemoryDenyWriteExecute=yes`. That directive makes the unit
**unbootable**: V8 allocates executable memory for JIT code, so node traps in
`SetPermissionsOnExecutableMemoryChunk` with `Check failed: 12 == errno`
(ENOMEM) and systemd reports `status=5/TRAP` plus a core dump.

The crash lands *before* `app.js` runs, which defeats the entire point of the
unit — its fail-closed credential check was unreachable. Fixed in PR #52
(`41ab86e`); the reason is recorded in the unit file itself.

All other hardening directives remain: `ProtectSystem=strict`, `NoNewPrivileges`,
`PrivateTmp`, `PrivateDevices`, `ProtectHome`, `ProtectKernelTunables`,
`ProtectKernelModules`, `ProtectControlGroups`, `RestrictAddressFamilies`,
`RestrictSUIDSGID`, `LockPersonality`.

## Not done, and why

**No GitHub App registration.** Requires an interactive browser session:
`POST /orgs/Aftergraph/app-manifests` returns 404 for a PAT (it needs a GitHub
OAuth client), and the browser stack on the workstation times out after 420s even
on `api.github.com/meta`. The private key is downloadable exactly once, so it has
to be generated by a person.

The org has 4 existing installations — `chatgpt-codex-connector`, `grok-by-xai`,
`claude`, `mistralai` — all third-party. `sentinel-github-app` does not exist yet.
`JonasAbde` holds `role: admin` in the org, so registration is permitted.

**No Cloudflare tunnel.** `cloudflared` 2026.9.3 **is** installed at
`/usr/local/bin/cloudflared`, but there is no `cert.pem` and no Cloudflare API
token on this host or the workstation, so the tunnel cannot be provisioned
non-interactively. `cloudflared tunnel list` fails with
`Cannot determine default origin certificate path`.

The webhook also needs a public URL before a GitHub App can be pointed at it.
Until a tunnel exists, GitHub has nowhere to deliver events.

**Tailscale Funnel is configured but NOT publicly reachable.** Verified on
2026-10-01, so do not trust `tailscale funnel status` alone:

```bash
ssh vds 'tailscale funnel status'      # prints "Funnel on"  <-- misleading
ssh vds 'tailscale debug prefs'        # AdvertiseServices: None  <-- the truth
```

All four handlers are configured and correct — `/` -> 7850, `/worksapi` -> 18191,
`/webhooks/github` -> 8788, `/api/platforms/google_chat/events` -> 8642 — and the
node holds a valid public certificate for `vmi3517816.tail59667c.ts.net`. But
the node never advertises the funnel service to the control plane, so the
endpoint stays tailnet-only.

The decisive test is always an **external** probe, never a tailnet-internal one:

```bash
curl -s "https://r.jina.ai/https://vmi3517816.tail59667c.ts.net/webhooks/github"
# ERR_CONNECTION_CLOSED  ->  not public
```

Two independent external fetchers (`api.allorigins.win`, `r.jina.ai`) both fail
this way today. A tailnet-internal `curl` to the same URL returns 200 and proves
nothing — the workstation is inside `tail59667c`.

`tailscale funnel reset`, re-applying every handler, and restarting `tailscaled`
all leave `AdvertiseServices: None`. The binary does support Funnel, so the
remaining suspects are tailnet admin policy or the control plane refusing the
advertisement; neither is fixable from this host.

**Consequence:** a GitHub App must not be created against this URL yet. App
creation is one-shot and the private key downloads exactly once, so registering
against an unreachable endpoint burns the credential on a permanently dead
webhook. Fix exposure first, verify externally, then register.

## Bring-up order once the key exists

1. `scp github-app.pem vds:/tmp/` then
   `install -o root -g sentinel -m 0640 /tmp/github-app.pem /etc/sentinel/github-app.pem && rm /tmp/github-app.pem`
2. In `/etc/sentinel/github-app.env` set `GITHUB_WEBHOOK_SECRET`, `GITHUB_APP_ID`,
   and optionally `GITHUB_INSTALLATION_ID`; leave `GITHUB_TOKEN` empty in App mode.
3. `systemctl start sentinel-github-app.service && systemctl status sentinel-github-app.service`
4. Confirm the listener: `ss -ltnp | grep :8788`
5. Provision the tunnel to `http://127.0.0.1:8788`, then set the same URL plus
   the webhook secret on the GitHub App registration.
6. Verify with a signed redelivery from the App's "Recent Deliveries" page.
   A 401 means the secret differs; a 404 means the path or method is wrong.

## Reinstall after a pull

```bash
cd /root/sentinel-src && git pull --ff-only origin main
bash ops/deploy/install.sh          # idempotent
install -m 0644 ops/deploy/sentinel-github-app.service /etc/systemd/system/
systemctl daemon-reload && systemctl start sentinel-github-app.service
```

`install.sh` only writes `/etc/sentinel/github-app.env` when it is absent, so a
filled env survives a redeploy. It will reset `PORT` to 8787 only if you delete
the file — keep 8788.
